# NFS-e Site Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After a premium report is delivered, the site captures the payer (CPF/CNPJ + name), asks the external NFS-e emitter to issue the invoice, shows it on the report page below the authenticity block, e-mails the PDF, and cancels it on refund, without ever slowing or breaking the sale flow.

**Architecture:** One adapter (`server/utils/nfse-provedor.ts`) wraps the emitter's HTTP contract; one orchestrator (`server/utils/nfse.ts`) decides whether to issue and records `nfse_*` columns; a webhook route and a reconciliation job keep state in sync. Every call from the sale flow is `void emVoo(...)` with a 3 s timeout, so the report, its e-mail and refunds never wait on the emitter. Payer data lives only in `pedidos_tomador`, AES-256-GCM encrypted with a server key.

**Tech Stack:** Nuxt 3 / Nitro (TypeScript), Supabase (Postgres), vitest, Resend via `premium-email.ts`, Node `crypto`.

**Spec:** `docs/superpowers/specs/2026-11-12-nfse-design.md` (§4.1, 4.2, 4.5, 4.6, 4.7 site parts, §8 texts, §9.1, §9.5). Emitter contract: spec §4.8; emitter plan in repo `nfse-emissor`.

## Global Constraints

- Public repo: no real CPF, token, e-mail, order id or key in code, tests, fixtures or commits. Fixture CPF `123.456.789-09`, CNPJ `12.345.678/0001-95`. Commits and PR text in English. Never `git add -A`.
- No em dash in any user-facing text. No "SENATRAN" in public copy. Provider names never in public copy.
- Customer e-mail only via Resend from `contato@`, inside the official layout (`montarEmailAviso` in `server/utils/premium-email.ts`).
- Feature flag `NUXT_NFSE` (`on`), envs `NUXT_NFSE_URL`, `NUXT_NFSE_API_KEY`, `NUXT_NFSE_WEBHOOK_SECRET`, `NUXT_NFSE_DESDE`, `NUXT_TOMADOR_KEY` (32 bytes base64). Everything off by default; with the flag off nothing is called and nothing is rendered.
- **Non-blocking (spec §9.5):** every emitter call from `premium-processar.ts`, `reembolsar.post.ts`, `status.get.ts`, webhooks and `report.get.ts` is `void emVoo(nome, fn)`; `$fetch` timeout 3000 ms; errors only `console.warn` with the order id truncated to 8 chars. No new `await` in the delivery path.
- Out of scope orders (spec §9.1): `pix_provider = 'google_play'` or `canal = 'app'` without `abacatepay_id`/`stripe_session_id` → `nfse_status = 'fora_escopo'`. Orders with `entregue_em` earlier than `NUXT_NFSE_DESDE` (ISO timestamp of activation) → `fora_escopo`.
- `nfse_status` values (exact): `a_enfileirar`, `enfileirada`, `emitida`, `rejeitada`, `falhou`, `sem_tomador`, `cancelada`, `cancelamento_rejeitado`, `fora_escopo`, `nao_emitir`.
- Migrations go to `supabase/migrations/` (applied to staging and prod by the Lead, not by the implementer).

## Review Focus

1. Emitter down when the report is delivered: delivery and e-mail must still succeed, `nfse_status = 'a_enfileirar'`, and the reconciliation job enqueues later (Task 4 test `emissor fora nao trava entrega`; Task 7 test `job enfileira a_enfileirar`).
2. Webhook with a bad HMAC or replayed body must change nothing (Task 6 test `assinatura invalida`).
3. Refund of an order whose invoice is still `enfileirada` must end as `nao_emitir` on both sides (Task 8 test `estorno antes da nota`).
4. Woovi charge without `payer.taxID` (card via Woovi, or payer omitted): order goes `sem_tomador` and Cesar gets one e-mail without the CPF (Task 2 and Task 4 tests).
5. Report page for an order with `nfse_status = 'emitida'` but the emitter unreachable when the PDF is requested: the block still renders; the PDF route returns 503 with a short message, never a 500 stack (Task 5 test `pdf indisponivel`).

### Task 6: Webhook route and invoice e-mail

**Files:**
- Create: `server/api/premium/nfse/webhook.post.ts`, `server/api/premium/nfse/webhook.test.ts`
- Modify: `server/utils/premium-email.ts` (add `montarEmailNfse`, `enviarNfseEmail`), `server/utils/nfse.ts` (add `aplicarEstadoNfse`)

**Interfaces:**
- Route: raw body; verify `X-Nfse-Assinatura: sha256=<hmac>` with `config.nfseWebhookSecret` using `crypto.timingSafeEqual`; 401 on mismatch; body `{ evento, nota }`; find order by `nota.referencia`; `aplicarEstadoNfse(supabase, pedido, nota)`; always 200 `{ ok:true }` after a valid signature (log only if order not found).
- `aplicarEstadoNfse(supabase, pedido, nota: NfseNota, deps)`: maps `nota.estado` → `nfse_status` (same names), copies `numero, serie, chave_acesso, emitida_em, cancelada_em, erro.codigo`, sets `nfse_atualizado_em`; when the new status is `emitida` and `pedido.email` and `nfse_email_em` is null → `enviarNfseEmail` then set `nfse_email_em`. Idempotent: same payload twice sends one e-mail.
- `montarEmailNfse({ link, placa, numero })` via `montarEmailAviso`: assunto `Sua nota fiscal do relatório da placa {PLACA}`, titulo `Nota fiscal emitida`, paragrafos `['Emitimos a nota fiscal de serviço do seu relatório. Ela vai em anexo e também fica disponível na página do relatório, abaixo do código de verificação.']`, botao `Ver meu relatório`, nota `''`. `enviarNfseEmail({ email, token, placa, numero, pdf: Buffer })` → Resend with `attachments: [{ filename: 'nfse-<numero>.pdf', content: base64 }]`, from `PlacaCompleta <contato@placacompleta.com.br>`; the PDF comes from `provedor.pdf(nfse_id)`; if the PDF fetch fails, do not send: leave `nfse_email_em` null so the reconciliation job retries.
